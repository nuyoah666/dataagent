> 7 篇业界实践（美团 Agent 评测、腾讯 SkillTrustBench、阿里 skill-up、得物记忆架构、
> 以及 3 篇 token/上下文成本优化）对照本项目的取舍。
>
> **一句话立场**：个人项目不追「评测平台 / 记忆中台」，追「每个 LLM 开放点都可量化、
> 可回归、可解释」。确定性的事交给规则与配置，开放的事才交给 LLM，贵的事尽量用工程手段摊薄。

## 1. 评测：对象是「系统」，不是「模型」

业界共识（①⑤）：Agent 评测至少覆盖 **结果层 / 过程层(轨迹) / 效率层 / 风险层**；
评测对象是「模型 + Prompt + 工具 + 记忆 + 流程」的整体；golden set 要**围绕高风险路径
设计**，不是线上随机抽样（线上样本有幸存者偏差，正常流程占绝大多数，真正出错的边缘场景
占比极低）；指标分 **P0 上线门禁 / P1 版本对比 / P2 长期观测**；LLM-as-judge 要先和人工
校准到 ~85% 一致率，且同系模型有「自偏好」，应用异系模型对抗打分。

| 业界做法 | 本项目现状 | 取舍 |
|----------|-----------|------|
| 结果层：任务是否完成、输出可用 | `eval_golden.py` 27 条确定性断言（intent/integration/etl/ops/trajectory） | ✅ 已做 |
| 过程层：轨迹/工具调用是否合理 | `eval_trajectory.py` + 结构化 `trace_step` + LangSmith 全链路 | ✅ 已做 |
| 效率层：token / 延迟 / 调用次数 | `llm_usage` 埋点，LLM 评测报告统计 token、缓存命中、耗时 | 🔨 有数据，缺「轨迹健康」判定（见 §2） |
| 风险层：越权 / 误操作 / 注入 | 审批门禁、`validate_identifier`、凭据脱敏、分析 SQL 只读守卫、审计留痕 | ✅ 已做 |
| 线上回流 → golden（数据飞轮） | bad case 重放晋升 + good case 零成本快照（防漂移） | ✅ 已做 |
| P0 门禁 / P1 对比 / P2 观测分层 | golden 与 LLM 评测目前靠手动跑 | 🔨 建议加一键门禁脚本（见 §5-1） |
| judge 校准 + 异系对抗 | judge 为可选项 | 🔨 保持「结构化断言为主、judge 仅主观项」；judge 用异系模型；写进约定即可 |
| 多轮 Session 层评测 | 已有跨会话指代（`conversation.py`），用例偏单轮 Turn | 🔨 补 1–2 条多轮 golden 即可 |
| skill-up 式 yaml 声明式评测 | 脚本式评测 | ❌ 单人项目脚本更直白可读，不引框架 |
| 全链路回放沙箱 / 报告归因平台 | — | ❌ 平台化，过度工程 |

**面试可讲**：「评测不是上线前抽查，而是嵌入研发的回归网。我们把 LLM 开放点冻结成 golden，
确定性流程走离线断言（515 单测 + 27 golden，CI 双平台跑），开放点走真实 LLM 结构化断言；
线上失败用 bad case 补短板、成功用 good case 定防漂移基线。」

## 2. 成本与上下文：模型负责生成，Harness 决定发什么、何时停

业界杠杆（③④）：**显式前缀缓存**（稳定 system/tools 放最前，吃缓存折扣）+ **上下文裁剪**
（少发探索结果、截断工具返回）+ **模型路由**（分类/标题等一次性简单活用便宜模型，主对话用
旗舰）+ 工具/MCP 延迟加载 + **杀掉无效轮次**。博客④把几十万 token 的 session 压成几千 token
结构化 JSON 做诊断，识别**病态轨迹**：零工具调用却空谈、同一工具同参数调 ≥3 次、单工具错误
率 ≥50%、调了 ≥5 个工具仍无结论。

| 业界做法 | 本项目现状 | 取舍 |
|----------|-----------|------|
| 模型路由（贵活/便宜活分模型） | 每类 Agent 可独立配模型，另设 `AGENT_CLASSIFY_MODEL` 便宜模型槽位给分类/指代 | ✅ 已做 |
| 前缀缓存友好 | 稳定前缀前置；`cached_tokens` 已埋点可看命中率 | ✅ 已做 |
| 工具/RAG 结果截断 | RAG / web 结果截断后再入 prompt | ✅ 已做 |
| 病态轨迹自动体检（过程+效率层） | 失败有运维 Agent 诊断；成功轨迹无「健康扫描」 | 🔨 **建议补 `scripts/lint_traces.py`**（见 §5-2） |
| 显式上下文缓存 API | 取决于火山/DeepSeek 是否支持 | ❓ 支持则开；不支持则靠稳定前缀吃自动缓存 |
| MCP 工具延迟加载 | 工具数量少 | ❌ 收益微，不做 |

## 3. 记忆：数仓 Agent 的「稳定事实」应进配置，不进模糊记忆

业界（⑦得物）：Working / Session / User / Agent 四层记忆；短期滑窗（Redis 热 + MySQL）、
长期语义检索（MemOS/Mem0）、并行加载、按 scope 分配 token budget、会话结束异步沉淀、
去重 / 冲突解决 / 先写后删。

**本项目刻意只做 Session 层的一小段**，这是一个明确的架构取舍（也是面试加分点）：

- **会话指代（模糊、需要记忆）**：✅ `conversation.py` 做跨会话指代消解——命中指代词
  （「刚才那个表」「还是同步到 ES」）才把上一任务的**结构化 intent 摘要成一行 hint** 注入，
  表名抽取始终以当前指令优先。不拼自由形态历史。
- **用户/Agent 长期记忆（中台）**：❌ 不建。理由：数仓 Agent 的「稳定事实」——数据源连接、
  ODS/DWD 命名规范、码值映射、语义层指标/维度定义——是**确定性资产**，应落在语义层 catalog、
  `dim_mapping` 码值表、DataX 模板、数据源配置里，可版本化、可审计、可回归。放进向量记忆
  反而不可控、不可回归，与「确定性防线」哲学冲突。**记忆只承接「会话指代」这一个真正模糊的点。**
- **滑窗 / token budget**：🔨 多轮拼接处加长度上限即可，不需要 Redis/MemOS 这套基础设施。

> 一句话：**「会变的偏好」才配进记忆，「不变的事实」必须进配置。**

## 4. 安全：一方工具走「安全编码清单」，不追供应链扫描

业界（②）：Agent Skill 成为新攻击面/供应链入口，常见问题是硬编码凭据、权限滥用、命令注入；
高召回扫描器误报多、高精度扫描器会漏报，LLM 扫描器跨模型偏好不稳。

本项目**没有第三方 Skill 市场**，MCP 工具均为一方，供应链投毒风险 N/A。对照一方工具的
安全编码清单：

| 风险 | 本项目对策 | 状态 |
|------|-----------|------|
| 硬编码凭据 | 凭据脱敏（`***`）、审计只存定位信息不存密码 | ✅ |
| 标识符注入（DROP/跨库） | `validate_identifier` 白名单校验表名/字段 | ✅ |
| 写操作误触发 | 集成/ETL 等写操作走人工审批门禁 | ✅ |
| 分析 Agent 误写库 | 问数 SQL 只读守卫（禁 INSERT/DELETE/...） | ✅ |
| MCP 侧门绕过 | 需确认 MCP 写工具与 HTTP 走**同一套**校验/审批 | 🔨 见 §5-3 |
| 第三方 Skill 扫描器 | 无第三方 Skill | ❌ 不做 |

## 5. 采纳清单（按 ROI 排序，贴合个人项目克制原则）

**P0（便宜、确定性、面试密度高）**

1. **评测门禁脚本 `scripts/eval_gate.py`**：串起 golden（必跑）+ LLM 质量（可选 `--llm`），
   P0 不通过则非 0 退出；README / CI 标注「发版前一键过门禁」。把①⑤的「门禁嵌入流程」落地。
2. **轨迹体检 `scripts/lint_traces.py`**：离线扫 `tasks.db` 已完成任务的轨迹，命中病态模式
   （同工具同参 ≥3 次、单工具错误率 ≥50%、≥5 工具无结论、轮次/耗时异常长）即报黄。
   把①的「过程层 + 效率层」和④的病态轨迹规则变成确定性、可回归的检查。
3. **MCP 写路径同源校验核对**：确认 MCP 暴露的写工具复用审批/标识符校验，补测试，避免 MCP
   成为绕过门禁的侧门。

**P1（锦上添花）**

4. 补 1–2 条多轮/跨会话指代 golden。
5. judge 异系模型 + 校准口径写进文档。

**明确不做（避免过度工程、远离 MVP）**

- 评测平台 / 全链路回放沙箱 / 报告归因系统；
- skill-up 式 yaml 评测框架（脚本更适合单人）；
- MemOS / Redis / MySQL 长期记忆中台（稳定事实进配置即可）；
- 第三方 Skill 安全扫描器（无第三方 Skill）。
